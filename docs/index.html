FixAcceptor

A minimal QuickFIX/n based FIX 4.4 acceptor (server) built on the .NET Generic Host. Accepts client connections on TCP 5001, auto-fills incoming NewOrderSingle orders, and broadcasts raw FIX messages to all logged-on sessions from text files dropped into a watched directory (one FIX message per line).

Overview

FixAcceptor is a lightweight FIX engine harness intended for development, testing, and integration scenarios where you need a predictable server-side counterparty to a FIX initiator (client). It demonstrates two common patterns at once:

  • Synchronous echo — incoming NewOrderSingle (35=D) messages are immediately answered with a FILLED ExecutionReport (35=8).
  • Asynchronous push — drop a text file of raw FIX messages (one per line) into the executions/ folder and the server forwards each one to every active session.

The project uses Microsoft.Extensions.Hosting with constructor-injected dependencies, keeps protocol concerns in Fix/, and isolates IO-bound work in Services/.

Architecture

Two hosted services run side-by-side under a single IHost. They communicate only through the thread-safe SessionRegistry, so neither side needs to know the other exists.

+-----------------------+ +----------------------------------+ | FIX Client(s) | TCP | FixAcceptorHost | | (initiator, port +------->| ThreadedSocketAcceptor :5001 | | 5001 outbound) | 35=D | | | +-----------------------+ | v | | FixServerApp (IApplication) | | | OnLogon / OnLogout | | | FromApp -> Crack | | v | | FixMessageHandler --(35=8)---->| | | | | v | | SessionRegistry (concurrent) | +----------^---------------+-------+ | | GetActiveSessions | | Register/ | | Unregister +----------+----------+ | | ExecutionFileWatcher| | | FileSystemWatcher | | | | | | | v | | | ExecutionFileProcessor | | read .json -> validate | | -> broadcast 35=8 | +--------------------------+ ^ | drop *.json executions/ (watched) | v executions/processed/ (archived)

Getting Started

Prerequisites

  • .NET 9 SDK — the project targets net9.0.
  • QuickFIXn.Core 1.14 and QuickFIXn.FIX44 1.14 — resolved via NuGet on first build.
  • A FIX client (initiator) configured to connect to localhost:5001 with SenderCompID=CLIENT and TargetCompID=SERVER.

Build & Run

powershell
# From the repository root
dotnet restore FixAcceptor.sln
dotnet build FixAcceptor.sln -c Release

# Run the acceptor
dotnet run --project src/FixAcceptor/FixAcceptor.csproj

On startup the console clears, prints ******** FIX Client ****************, and the acceptor begins listening on port 5001. The executions/ watch folder and its processed/ archive are created on first run under the build output directory.

Tip Both the store/ and log/ directories used by QuickFIX/n are created relative to the working directory. To start fresh, stop the host and delete those folders to reset sequence numbers.

Configuration

server.cfg

The QuickFIX/n session configuration is loaded from server.cfg at startup by SessionSettingsProvider. The file is copied to the output directory on build.

server.cfg
[DEFAULT]
ConnectionType=acceptor
StartTime=00:00:00
EndTime=23:59:59
HeartBtInt=30
FileStorePath=store
FileLogPath=log
UseDataDictionary=Y
DataDictionary=FIX44.xml
ValidateUserDefinedFields=N
AllowUnknownMsgFields=Y

[SESSION]
BeginString=FIX.4.4
SenderCompID=SERVER
TargetCompID=CLIENT
SocketAcceptPort=5001

Notable choices:

  • StartTime=00:00:00 / EndTime=23:59:59 — the session is always open.
  • HeartBtInt=30 — the server expects a 30-second heartbeat from any logged-on client.
  • AllowUnknownMsgFields=Y — keeps the engine permissive when clients add custom tags.

Data Dictionary

All eight standard FIX XML dictionaries (FIX 4.0 through FIX 5.0 SP2) ship in DataDictionaries/. Only FIX44.xml is linked into the build output, since the session is hard-coded to BeginString=FIX.4.4. To support a different version, change BeginString / DataDictionary in server.cfg and add the dictionary as a None Include in FixAcceptor.csproj.

Connecting a Client

A sample QuickFIX/n initiator config that pairs with this acceptor lives at docs/client.cfg. It is the mirror image of server.cfg: ConnectionType=initiator, SenderCompID / TargetCompID swapped, and the listening port replaced by SocketConnectHost / SocketConnectPort.

docs/client.cfg
[DEFAULT]
ConnectionType=initiator
ReconnectInterval=5
HeartBtInt=30
FileStorePath=store
FileLogPath=log
UseDataDictionary=Y
DataDictionary=FIX44.xml
ValidateUserDefinedFields=N
AllowUnknownMsgFields=Y
StartTime=00:00:00
EndTime=23:59:59

[SESSION]
BeginString=FIX.4.4
SenderCompID=CLIENT
TargetCompID=SERVER
SocketConnectHost=127.0.0.1
SocketConnectPort=5001

Field-by-field mapping to the server config:

SettingServerClientWhy it pairs

BeginStringFIX.4.4FIX.4.4Must match exactly.
SenderCompIDSERVERCLIENTSwapped — server expects messages whose sender is CLIENT.
TargetCompIDCLIENTSERVERSame reason, inverted.

Wire the file into a QuickFIX/n initiator (SocketInitiator or ThreadedSocketInitiator) and copy FIX44.xml from DataDictionaries/ into the client's output directory — same trick the server's csproj uses with the linked None Include.

Sequence numbers persist on both sides QuickFIX/n stores per-session sequence numbers under FileStorePath for both acceptor and initiator. If you reset one side, reset the other (delete both store/ dirs) or the next logon will be rejected with a sequence-number mismatch.
Same-machine setup Run the client from a different working directory than the server so they don't share store/ and log/ folders. The defaults are relative paths, so simply launching each from its own output directory is enough.

Core Components

Program & Dependency Injection

Program.cs wires up the generic host. All services are singletons (each is intrinsically thread-safe or stateless), and two are registered as IHostedService so they start with the host:

src/FixAcceptor/Program.cs
var builder = Host.CreateApplicationBuilder(args);

builder.Services.AddSingleton<ISessionSettingsProvider, SessionSettingsProvider>();
builder.Services.AddSingleton<ISessionRegistry, SessionRegistry>();
builder.Services.AddSingleton<IFixMessageHandler, FixMessageHandler>();
builder.Services.AddSingleton<IExecutionFileProcessor, ExecutionFileProcessor>();
builder.Services.AddSingleton<FixServerApp>();
builder.Services.AddHostedService<FixAcceptorHost>();
builder.Services.AddHostedService<ExecutionFileWatcherService>();

FixServerApp

Implements QuickFIX/n's IApplication by extending MessageCracker. Lifecycle callbacks (OnCreate, OnLogon, OnLogout) update the SessionRegistry. FromApp delegates message dispatch to Crack(...), which routes NewOrderSingle instances to the typed OnMessage overload:

Fix/FixServerApp.cs
public void OnLogon(SessionID sessionId)
{
    _logger.LogInformation("Logon: {SessionId}", sessionId);
    _sessionRegistry.Register(sessionId);
}

public void FromApp(Message message, SessionID sessionId)
{
    var msgType = message.Header.GetString(QuickFix.Fields.Tags.MsgType);
    _logger.LogInformation("FromApp [{MsgType}]: {SessionId}", msgType, sessionId);
    Crack(message, sessionId);
}

public void OnMessage(QuickFix.FIX44.NewOrderSingle order, SessionID sessionId)
{
    _handler.HandleNewOrderSingle(order, sessionId);
}

FixAcceptorHost

IHostedService wrapper around ThreadedSocketAcceptor. StartAsync builds a FileStoreFactory (message store) and ScreenLogFactory (FIX wire log to console), then starts the acceptor. StopAsync stops and disposes it on shutdown.

FixMessageHandler

Translates a NewOrderSingle into a fully-populated ExecutionReport, sets ExecType=FILL / OrdStatus=FILLED, then routes the response with Session.SendToTarget(...). The fill is synthetic: every order is reported as completely filled at price 100.0.

Services/FixMessageHandler.cs
public static QuickFix.FIX44.ExecutionReport BuildExecutionReport(
    string clOrdId, string symbol, char side, decimal orderQty)
{
    var orderId = Guid.NewGuid().ToString("N");
    var execId  = Guid.NewGuid().ToString("N");

    var execReport = new QuickFix.FIX44.ExecutionReport(
        new OrderID(orderId),
        new ExecID(execId),
        new ExecType(ExecType.FILL),
        new OrdStatus(OrdStatus.FILLED),
        new Symbol(symbol),
        new Side(side),
        new LeavesQty(0m),
        new CumQty(orderQty),
        new AvgPx(100m));

    execReport.Set(new ClOrdID(clOrdId));
    execReport.Set(new LastQty(orderQty));
    execReport.Set(new LastPx(100m));

    return execReport;
}

SessionRegistry

Thread-safe directory of currently logged-on SessionIDs backed by a ConcurrentDictionary. FixServerApp writes to it on logon/logout; ExecutionFileProcessor reads from it when broadcasting.

Services/SessionRegistry.cs
public class SessionRegistry : ISessionRegistry
{
    private readonly ConcurrentDictionary<string, SessionID> _sessions = new();

    public void Register(SessionID sessionId)   => _sessions.TryAdd(sessionId.ToString(), sessionId);
    public void Unregister(SessionID sessionId) => _sessions.TryRemove(sessionId.ToString(), out _);

    public IReadOnlyCollection<SessionID> GetActiveSessions() => _sessions.Values.ToList();
    public bool HasActiveSessions()                           => !_sessions.IsEmpty;
}

ExecutionFileWatcherService

Background service that monitors {baseDir}/executions/ for newly-created *.json files via FileSystemWatcher. Each new file is gated by WaitForFileReadyAsync (a 10-attempt, 100ms polling loop that opens the file exclusively) to avoid reading a partial write. On success the file is passed to ExecutionFileProcessor and then moved to executions/processed/ with a UTC timestamp suffix.

Note on errors If ProcessFileAsync throws, the file is intentionally not moved so a human can inspect it. Re-running the host will pick it back up the next time it appears as a created file — manual deletion or re-drop may be required.

ExecutionFileProcessor

Reads the file as a list of raw FIX messages — one per line — parses each into a QuickFix.Message, and sends it to every active session via Session.SendToTarget. No field-level validation or builder logic: whatever the line contains goes on the wire (after the engine rewrites session-managed headers).

  • Blank and whitespace-only lines are skipped.
  • Pipe-delimited dumps (|) are normalized to wire-format SOH (\x01) before parsing; files already using SOH are passed through unchanged.
  • Messages are parsed with validate: false — stale or missing BodyLength (9) and CheckSum (10) are tolerated because QuickFIX/n recomputes both during serialization.
  • Per-message parse failures are logged and skipped; the remaining lines still go out.

If no sessions are logged on, the processor logs a warning and returns without sending. The file is still moved to processed/ because no exception was thrown — re-drop the file once a client has connected to deliver it.

Execution File Format

Drop a UTF-8 text file into executions/. The file watcher's glob is *.json for historical reasons, but the file contents are raw FIX messages — one per line, not JSON. Use the .json extension so the watcher picks the file up.

Each non-blank line is parsed into a QuickFix.Message and forwarded to every logged-on session via Session.SendToTarget. The engine rewrites the session-managed headers (BeginString, SenderCompID, TargetCompID, MsgSeqNum, SendingTime) and recomputes BodyLength / CheckSum before sending, so the values in your file for those tags are advisory at best.

executions/sample.json (pipe-delimited)
8=FIX.4.4|9=148|35=8|49=SERVER|56=CLIENT|34=1|52=20260517-12:00:00.000|37=ORDER1|11=ORD-1001|17=EXEC1|150=F|39=2|55=AAPL|54=1|151=0|14=100|6=195.42|31=195.42|32=100|10=000|
8=FIX.4.4|9=148|35=8|49=SERVER|56=CLIENT|34=2|52=20260517-12:00:00.000|37=ORDER2|11=ORD-1002|17=EXEC2|150=F|39=2|55=MSFT|54=2|151=0|14=50|6=380.10|31=380.10|32=50|10=000|
ConventionWhat it means
One message per lineThe watcher reads the whole file, then iterates lines. Blank and whitespace-only lines are skipped.
| as separatorReplaced with the wire-format SOH byte (\x01) before parsing — convenient for hand-editing.
SOH already presentLine is passed through unchanged. Don't mix the two on the same line.
Stale tags 9 / 10Ignored. BodyLength and CheckSum are recomputed on serialization.

Workflows

Synchronous Order Echo

  1. Client connects to localhost:5001 and sends a Logon (35=A).
  2. FixServerApp.OnLogon registers the SessionID.
  3. Client sends NewOrderSingle (35=D).
  4. FromApp cracks the message; OnMessage(NewOrderSingle, ...) delegates to FixMessageHandler.
  5. A fully-filled ExecutionReport (35=8) with fresh OrderID / ExecID is returned on the same session.

Asynchronous File-Drop Broadcast

  1. Drop my-fills.json into the executions/ directory (created on first run, under the build output).
  2. ExecutionFileWatcherService sees the Created event and waits until the file is readable.
  3. ExecutionFileProcessor reads the file line-by-line, normalizes | to SOH where needed, and parses each line into a QuickFix.Message.
  4. Each parsed message is forwarded to every session in SessionRegistry via Session.SendToTarget; QuickFIX/n overwrites session-managed headers and recomputes BodyLength / CheckSum on the wire.
  5. On success the file is moved to executions/processed/{name}_{yyyyMMdd_HHmmss}.json.

Testing

xUnit tests live under tests/FixAcceptor.Tests/ and cover four areas:

  • ExecutionReportBuilderTests — builder shape, default price, GUID identifiers.
  • ExecutionFileProcessorTests — line splitting, blank-line skipping, pipe→SOH normalization, parse-error handling.
  • FixServerAppTests — logon/logout registration, cracker dispatch.
  • SessionRegistryTests — concurrent register/unregister behavior.

Troubleshooting

SymptomLikely causeFix
FileNotFoundException: QuickFIX config not found server.cfg not copied to the output directory. Confirm the <None Update="server.cfg"> entry in the csproj is present; rebuild.
Client cannot log on (sequence mismatch) State persisted in store/ from a previous run is out of sync with the client. Stop the host and delete the store/ directory under the output folder.
File dropped but no message sent No active sessions, or every line failed to parse. Check the log — no sessions are logged on at WARN, or Failed to parse FIX message at ERROR.
File silently never processed Locked by another process; WaitForFileReadyAsync gave up after 10 attempts. Write the file atomically (write to a sibling name, then rename) so it is fully flushed before FileSystemWatcher fires.
